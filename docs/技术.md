# 后端实习面试：项目技术准备

这个项目已经有足够的业务复杂度，不必靠堆 Redis、RabbitMQ、微服务来“凑架构”。准备重点是：**把一条真实调用讲透，把授权和失败语义讲清楚。**

面试官通常不是要求实习生背下所有代码，而是判断：有没有真正做过，能不能解释取舍，出了问题有没有定位能力。

> 本文是面试准备笔记，不是全部功能均已实现的声明。当前单体已经上线；分布式和用户系统属于设计。审批成功后向 Agent 返回密码也是待实现设计。
>
> 提问按“开放的主问题 → 根据回答继续追问”组织。具体字段名、状态名和代码结构，通常在自己介绍后才会被追问；复习检查点不代表面试官一定会这样问。

## 一、必须自己掌握的内容

### 1. 项目到底解决什么问题

**面试问题：简单介绍一下你这个项目。**

**可能追问：**为什么想做这个？和已有的远控工具有什么区别？

**参考回答：**

> 我做的是面向 AI Agent 的远程协助平台。设备客户端主动连接中继服务，Agent 通过 MCP 申请设备会话，获得授权后执行 PowerShell 或传输文件。与传统远控不同，调用结果是结构化数据，不是屏幕画面。我的重点是授权边界、操作可见性，以及网络故障时不误报执行结果。

#### 为什么不是直接 SSH、RDP 或现成远控？

传统远控主要面向人操作桌面。我希望用 Agent 提高效率，把我这边配置好的模型和 Agent 能力用到普通用户的设备上，减少重复操作。

SSH 也可以自动化，但普通 Windows 用户配置服务、账号和网络的成本较高。我的目标是让他们安装客户端后，通过设备码、密码或审批接受协助。不是现成工具做不到，而是目标用户的部署条件和交互需求不同。

#### 可能追问：服务端怎么连接用户的电脑？

用户设备通常在 NAT 和防火墙后，没有可供平台直接访问的公网地址。因此设备主动向平台建立长连接，平台通过已有连接下发消息，不需要用户配置端口映射。

#### 可能追问：为什么要经过服务器，不考虑直连吗？

中继实现简单，不需要处理复杂的 NAT 穿透、打洞成功率和失败回退。当前已有服务器，优先用它获得稳定、可控的连接路径。代价是所有流量经过服务器，带宽和资源成本集中在平台。

#### 可能追问：现在做到什么程度了？有人实际用过吗？

- 单体已经上线运行。
- 分布式和用户系统目前是设计。
- 审批成功后向 Agent 返回密码尚未实现；持当前有效密码直接创建会话已经支持。

### 2. 一条命令完整经过哪些地方

**面试问题：讲一下执行一条命令的完整流程。**

**可能追问：**服务端在里面负责什么？执行结果怎么回到调用方？

**复习检查点：**校验位置、执行位置、结果存储位置。

**参考回答：**

```text
Agent → MCP Adapter → platformclient → 平台
     → 校验会话 → 设备连接 → PowerShell
     → 输出分块 → 平台缓存 → Agent 获取结果
```

**结合回答可能追问：你刚才提到设备、连接和会话，它们是什么关系？一条结果回来后，怎么知道属于哪次操作？**

**参考回答：**它们分别标识设备、当前连接、一次授权和一次操作，生命周期与用途不同，不能相互替代。


| 标识 | 作用 |
| --- | --- |
| `device_id` | 找哪台设备，不是授权凭据 |
| `connection_id` | 当前哪条网络连接 |
| `session_id` | 哪一次授权 |
| `request_id` | 哪一次操作，用于幂等与结果查询 |

不要求记住所有函数名，但要知道：状态放在哪、权限在哪验、命令在哪执行。

### 3. 授权模型

**面试问题：远程执行命令的权限是怎么控制的？**

**可能追问：**如果别人知道了我的设备码，能不能操作我的电脑？

**参考回答：**

- 平台密码只允许使用中继，不授予设备权限。当前只有一台 2C2G 香港服务器，需要限制平台资源被滥用。
- 设备码是公开标识和寻址地址，不是秘密。
- 当前临时密码或所有者批准，才构成设备授权。
- 会话绑定设备、操作者连接和有效期，避免串台并限制授权时长。
- 每次操作仍需校验会话，而不是“连接过就永久可信”。
- 所有者可以主动终止会话，保留对设备的控制权。

**结合回答可能追问：用户同意以后，这个权限会一直有效吗？后续请求怎么判断还能不能执行？**

**参考回答：**会话可能已经过期、关闭或中断，请求也可能来自不属于该会话的连接。每次操作都需要检查归属、状态、有效期和所需权限，不能把历史上的授权当成永久有效。

#### 设计追问：如果后续允许 Agent 保存密码，用户还能怎样限制它？

仅在介绍“审批后返回密码”的待实现设计后展开，不把它当成当前功能。

> 产品设计是允许 Agent 在密码有效期内再次创建会话，方便断联后自行重新申请，而不是实现旧会话无缝恢复。密码过期、轮换或撤销后，旧密码不能继续使用。

这意味着授权范围不只是“当前这一次会话”，还包括密码有效期内再次直连的能力，需要让所有者明确知晓。

**实现边界：审批成功后返回密码尚未实现，不能作为当前已有能力介绍。**

### 4. 并发模型和顺序保证

**面试问题：服务端收到请求以后是怎么处理的？并发这块怎么设计的？**

下面的追问应在介绍读写循环、发送队列等实现后展开。

#### 可能追问：为什么这样分读写？考虑过线程池或工作池吗？

每条连接独立读取消息，读循环同步调用 handler，避免同一连接的文件分块、命令输出和状态消息被并发处理后乱序。写侧统一消费发送队列，串行写入。

当前 handler 主要做校验、状态操作和转发，不在平台执行远端命令，也不承担长时间业务计算。真正的 PowerShell 执行在设备端，因此暂时不需要额外工作池。

代价是：同连接里如果某个 handler 很慢，会阻塞后续消息，因此不能在里面放长时间执行的业务。

#### 可能追问：多个请求同时要发消息，会不会有并发问题？

本项目采用单写者，统一控制应用消息写入和顺序。多个业务 goroutine 可以并发向发送 channel 入队，由一个写循环统一取出并写入连接。

`writeMu` 保护实际网络写入，因为致命错误响应可能绕过队列直接写，两条路径需要串行化。

```text
多个业务 goroutine
        ↓ 可以并发入队
outgoingMessages channel
        ↓ 一个写循环消费
编码 → 写网络连接
```

channel 支持并发发送，但多个发送者之间的业务顺序仍需要上游逻辑保证。

#### 可能追问：如果消息产生得比发送得快，会怎么样？

有界队列限制慢客户端造成的内存积压。当前容量是工程配置，需要结合指标和负载测试调整，不保证适合所有负载。

#### 继续追问：积压到上限以后，你现在怎么处理？

非阻塞入队；如果队列满，记录慢客户端事件，关闭该客户端连接，并返回转发失败。转发失败的命令可能被标为 `result_unknown`，断线也会触发会话和任务清理，具体结果取决于断开的是哪一端。

队列满也可能来自正常突发流量。更完善的方向是窗口限流或背压，当前采用的是简单的资源保护策略。

#### 可能追问：收到消息后，为什么不都开 goroutine 并发处理？

同一连接的消息虽然按顺序读到，但如果每收到一条就启动一个 goroutine，handler 的执行和完成顺序就可能改变。

例如先收到文件第 1 块，再收到第 2 块，第 2 块却先更新传输状态，就可能触发序号校验失败。因此当前读循环同步分发，处理完上一条再处理下一条，代价是慢 handler 会阻塞同连接后续消息。

**一个读循环不自动等于同步分发：顺序来自读取后同步执行 handler，而不是只看读循环数量。**

#### 可能追问：项目里哪些地方用了锁？举一个具体例子。

连接表和各 manager 内部的共享 map、可变记录，分别通过对应的锁保护。channel 本身支持并发使用，不需要因为多个生产者额外加锁。

锁不仅防止并发 map 访问出错，还要保护复合操作。例如检查 `request_id` 是否存在与创建任务，需要在同一临界区完成，避免重复创建。

> 单写者控制网络写入；有界队列限制内存积压；同步分发保证同连接处理顺序。代码可以由 AI 辅助实现，但这些取舍必须自己理解。

### 5. 幂等、断线和“不确定结果”

**面试问题：执行过程中断网了，你怎么处理？**

**场景追问：**比如一条删除命令发出去了，但没收到结果，这时候会怎么做？

**参考回答：

> 不能。网络断线无法证明命令没执行，因此结果应标为不确定，由 Agent 重新连接后检查现场，而不是自动重放。

**可能追问：调用方重复提交了同一个请求，会不会执行两遍？**

**继续追问：**换一次连接或者重启服务后，这个保证还在吗？

**复习检查点：**区分连接与会话；说明 `request_id` 的作用域和内存记录的生命周期。

**参考回答：**

- 同会话重复 `request_id`，返回已有任务，不重复执行。
- 跨会话复用 `request_id`，按当前规则报冲突。
- 新建会话不等于恢复旧任务。
- 当前幂等记录在内存里，不承诺跨进程重启的去重。
- `failed`、超时或取消，也不天然意味着“完全没有副作用”。

**可能追问：哪些情况你认为可以重试？超时或者报错就代表没有执行成功吗？**

**参考回答：**不一定。命令退出码非零，也可能已经修改了一半系统，不能把所有失败都描述成可安全重试。应先检查实际状态和可能产生的副作用。

## 四、准备优先级与速记

### 第一优先级：能画图、能追代码

#### 1. 授权与会话状态

**面试问题：用户是怎么授权一次远程协助的？**

**可能追问：**用户没同意、一直没回应，或者中途退出，分别怎么处理？

**复习检查点：**创建会话的时机、密码与审批两条路径、各终态的含义。

**参考回答：**

```text
平台认证通过
    ├─ 不带密码申请 → 创建 pending_approval 会话
    │                    ├─ 批准 → approved
    │                    ├─ 拒绝 → rejected
    │                    └─ 审批超时 → expired
    │
    └─ 带有效密码申请 → 创建 approved 会话

approved → active
会话按条件进入终态：closed / expired / interrupted
```

会话在请求时就已经创建，审批只是改变同一个会话的状态，不会再次建立 session。批准后的会话在进入 `active` 前，也可能因关闭、超时或断线而结束。

**待实现设计：**审批成功后向 Agent 返回密码，供有效期内创建新会话使用；不恢复旧会话，也不自动重放旧命令。

#### 2. 命令完整链路

**面试问题：拿执行命令这个功能，讲一下后端的处理流程。**

**可能追问：**哪些地方可能失败？重复调用会怎么样？

**参考回答：**

```text
Agent Host → MCP Adapter → platformclient → 后端服务器
          → 参数、会话归属、状态、权限与设备连接校验
          → 创建或查找幂等任务 → 转发给设备 → PowerShell 执行
          → 输出和结果回传 → 平台缓存 → 工具获取并返回结果
```

#### 3. 连接读写与并发安全

**面试问题：客户端和服务端怎么通信的？为什么选这个协议？**

**可能追问：**连接上的消息怎么收发？多个任务同时返回结果怎么办？

**介绍早期 TCP 方案后可能追问：**之前怎么实现的？为什么后来换了协议？

**复习检查点：**消息边界由哪层处理、业务消息如何关联、channel 入队与实际写连接的区别。此处答案侧重实现边界，协议选型理由需要结合实际迁移经历准备。

**参考回答：**

Go 业务层通过 transport 的 `ReadMessage` 获取完整消息，不需要自行处理 TCP 消息边界，仍需 JSON 解析、大小限制和字段校验。Qt 端基于 `QSslSocket` 维护 WebSocket 握手与帧解析

多个 goroutine 可以并发向发送 channel 入队，由单独写循环消费；`writeMu` 保护实际网络写入。连接表和各 manager 的共享状态由对应的锁保护。

#### 4. 会话与任务状态机

**面试问题：一条命令从提交到结束，你怎么管理它的状态？**

**可能追问：**调用方怎么知道它完成了？用户中途取消会怎么样？

**复习检查点：**会话与任务的职责、平台状态与设备实际执行的区别、取消请求与取消完成的区别。

**参考回答：**

会话状态回答“有没有操作资格”，任务状态回答“这条命令执行到哪里”。

当前任务创建后直接进入 `running`，之后进入以下终态之一：

```text
running
    ├─ succeeded
    ├─ failed
    ├─ timed_out
    ├─ cancelled
    └─ result_unknown
```

平台记录 `running` 不代表设备已经确认开始执行；取消请求也不等于进程已经停止。

#### 5. 幂等与不确定结果

**面试问题：请求超时后，调用方又发了一次，你怎么处理？**

**可能追问：**怎么避免重复执行？如果不知道第一次有没有执行成功呢？

**参考回答：**网络失败不代表命令没执行。通过同会话内的请求 ID 去重避免重复执行，跨会话复用 ID 则报冲突；结果不确定时返回 `result_unknown`，由 Agent 检查现场，不自动重放。详见第一节。

#### 6. 一个真实 bug 的定位过程

**结合排障经历可能追问：改完以后怎么验证的？这个问题后来还出现过吗？**

**回答准备：**使用第一节的代理连接问题，补齐实际验证配置，不编造未确认的根因。

### 第二优先级：理解原理和局限

#### 文件分块、序号、大小与哈希校验

**面试问题：文件传输是怎么实现的？怎么判断传完了、内容没问题？**

**介绍校验方案后可能追问：**为什么做这几层校验？文件校验通过就可以认为安全吗？

**参考回答：**

传输链路提供有序消息，接收端还要检查分块 `sequence` 连续、累计大小符合声明，接收完成后比对 SHA-256。序号用于发现缺块、重复或乱序，不是序号本身让消息按顺序到达。

哈希用于验证内容是否与可信的预期值一致，本身不能证明发送者身份，也不能判断文件是否恶意。

#### 临时文件校验后再改名

**面试问题：文件传到一半失败了，会留下什么？**

**介绍临时文件方案后可能追问：**为什么这样写？原来的文件会不会受影响？

**参考回答：**

先写临时文件，校验大小与内容后再原子改名，避免网络中断后把半成品作为完整目标文件暴露给用户。原子改名不等于跨重启恢复或断点续传。

#### 待补充理解的主题

以下只列准备问题，尚未补齐正式回答：

- [ ] **超时、取消与进程清理：**命令超时后谁发取消？如何清理子进程？平台发出取消是否就证明设备停止？
- [ ] **资源上限、慢客户端和背压：**哪些资源有上限？队列满时是拒绝、断线还是等待？背压与单纯扩容队列有什么区别？
- [ ] **TLS、密码哈希、凭证保护：**TLS 防什么？为什么保存密码哈希而不是明文？日志和设备本地凭据怎样保护？
- [ ] **全内存实现：**为什么不持久化？平台重启后哪些数据失效？这对查询和幂等保证有什么影响？

### 第三优先级：扩展思考，不急着实现

**面试问题：如果使用量上来了，现在这个架构怎么扩展？**

**复习检查点：**先讲当前瓶颈和测量依据，再讨论多网关；表中的具体追问仅在介绍相应方案后展开。

| 主题 | 对应追问 | 当前理解与边界 |
| --- | --- | --- |
| Redis 状态外置 | 多个实例需要共享哪些数据？ | 将需要跨网关共享的状态从进程内存搬到 Redis，例如设备码、密码哈希、墓碑、会话状态、权限、到期时间、任务状态与退出码。socket 不能搬走 |
| RabbitMQ 跨网关转发 | 两端连到了不同实例怎么办？为什么选这种转发方式？ | socket 留在所属网关，MQ 负责跨网关转发消息帧，每个网关有自己的队列并自行消费。Redis Pub/Sub 也可作为比较方案，但需要评估订阅端离线丢消息等语义，目前未实施验证 |
| 用户微服务 | 为什么先拆用户系统，而不是会话或任务模块？ | 新领域，适合建立独立服务边界，避免先拆分与连接生命周期强耦合的核心模块 |
| 分布式锁 | 多个实例同时处理同一份数据，会不会冲突？ | 待学习，不作为已有实践经验介绍 |
| 会话无缝恢复 | 断线后是恢复旧会话还是创建新会话？为什么？ | 当前不做；断线后由 Agent 使用有效凭据创建新会话 |

> 实习面试里，“把单机系统做扎实，并能解释扩展瓶颈”，通常比“接了多个中间件，但不知道故障语义”更有说服力。

## 五、内存越来越高，怎么排查

> 学习笔记：以下是排查方法，不代表已经完成 pprof 实践。

**面试问题：线上进程的内存越来越高，你会怎么定位？**

**复习检查点：**不要直接把内存上涨等同于泄漏；先看负载、存活对象与 goroutine 等指标。

**参考回答：**先区分三个概念：

| 现象 | 含义 |
| --- | --- |
| 累计分配很多 | 运行期间创建过很多对象，不代表现在还占着 |
| 存活对象很多 | 对象仍然被引用，GC 不能回收 |
| 进程内存较高 | 不一定都是存活业务对象，也可能包含运行时保留内存等 |

不能看到任务管理器里内存高，就直接说“Go 内存泄漏”。

### 第一步：让现象可重复

**可能追问：你会先看什么数据？这个现象怎么复现？**

**参考做法：**在测试环境：

1. 记录空闲内存。
2. 连续执行固定数量、固定输出量的命令。
3. 等所有任务完成。
4. 再重复一轮，观察是否持续增长。

同时记录：

- 会话记录数。
- 任务记录数。
- 缓存输出字节数。
- goroutine 数量。

先建立“增长和什么操作相关”，再找原因。

### 第二步：从代码提出假设

**介绍历史任务积压的猜测后可能追问：为什么怀疑这里？任务结束以后，这些数据还会保留吗？**

**复习检查点：**对象可达性，以及单任务上限和历史总量的区别。

**参考回答：**任务管理器包含任务 map，每个任务保存输出块：

```go
// 仅展示相关字段。
type Manager struct {
    tasks map[string]*Task
}

type Task struct {
    Chunks []Chunk
}
```

如果终态任务一直留在 `tasks` 中：

```text
Manager → tasks map → Task → Chunks → 输出字符串
```

这些对象始终可达，GC 就不能释放。

> “执行结束”只是业务状态改变，不等于对象自动从 map 删除。

单任务输出上限只能限制一条任务，不能限制历史所有任务的总和。

### 第三步：用 pprof 验证，而不是只凭猜测

**可能追问：用过什么分析工具？怎么验证你刚才的猜测？**

**复习检查点：**区分准备采用的方法与已经实践过的经历；知道 heap 和 goroutine profile 各自能提供什么信息。

**参考做法：**在本机或受保护的调试环境启用 pprof 后，采集两次 heap profile 进行比较。查看已采集文件的示例：

```bash
go tool pprof -http=127.0.0.1:8081 heap.pb.gz
```

重点看：

- `inuse_space`：当前存活对象占用。
- 哪些分配调用栈对应的存活内存持续增长。
- 是否集中在输出块追加、任务记录等路径。

heap profile 主要告诉你内存从哪里分配，不会直接完整展示谁持有这些对象。还需要回到代码检查引用关系和回收逻辑。

如果 goroutine 数持续增长，再看 goroutine profile，检查是否有大量协程卡在相同的 channel、锁或网络调用上。

### 第四步：修复后重复同一实验

**提出回收方案后可能追问：这个改动会不会影响其他功能？你打算怎么验证？**

**复习检查点：**结果查询保留期、幂等记录生命周期，以及相同负载下的前后对比。

**参考回答：**例如给终态任务增加 TTL 回收，但要同时考虑：

- 保留多久供 Agent 查询？
- 删除后幂等记录是否也消失？
- 是否需要将大输出和较小的幂等元数据分开保存？

参考回答：

> 我会先区分存活对象增长、分配频繁和 goroutine 泄漏。结合项目结构，优先检查终态任务和输出是否仍被 map 引用，再通过 heap profile 验证。修复后重复相同负载，看存活内存是否趋于稳定。

不用一开始就背完整 pprof 命令，但需要通过实践理解数据。

## 六、自测标准

**自测问题：不看笔记，随机选一条核心请求，能不能完整回答下面这些问题？**

- 为什么允许这次操作，凭据和授权分别是什么？
- 经过哪些组件和状态，在哪里更新共享数据？
- 哪些地方可能失败，能否确定命令未执行？
- 失败后留下哪些记录，能否查询，能否重试？
- 准备用什么测试或证据验证回答？

> 随机挑一条核心请求，能解释它为什么被允许、经过哪些状态、哪里可能失败、失败后会留下什么，以及如何验证。

AI 写了多少行不是最关键的，**能对多少行为负责才是**。
