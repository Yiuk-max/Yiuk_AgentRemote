# 分布式演进计划：Gateway 集群 · Core Service · User Service

状态：**P1 已实现，P2 起尚未实施**。P1 的落地形式见下面的“实施进度”与 §4.1，其余章节仍是设计计划。

目标是：**接入层可以多开，原有业务整体保留，新用户系统独立开发。每个组件都有明确用途，不为了拆服务而拆服务。**

## 实施进度

| --- | --- | --- |
| **P1：接入/业务分离** | 已完成 | `internal/platform/core`（业务）+ `internal/platform/gateway`（接入）+ `internal/platform/edge`（gRPC 契约）；`cmd/platform-core`、`cmd/platform-gateway` 两个进程，`cmd/platform` 保留单进程拼装 |

P1 的两项简化，与原始设计不同，以此为准：

1. **Core 不保存连接表**。连接表只在 Gateway；`connection_id` / `role` / `device_id` 存在连接对象上，随每次调用以 `Caller` 带进 Core、处理完带回去。Core 需要判断“某条连接还在不在”时就问 Gateway（`Alive`），自己不记账。
2. **gRPC 明文、不开 TLS**，只监听回环或容器内网。

## 1. 先明确做什么、不做什么

| 本次做 | 本次不做 |
| --- | --- |
| 将网络接入与业务处理分开 | 不把 Device / Session / Task 逐个拆成微服务 |
| 多个 Gateway 管理各自的客户端连接 | 不恢复断线前的旧会话，不引入 resume token |
| 原有设备、会话、任务、文件传输逻辑整体迁到 Core Service | 不一开始就做 Core 集群、分布式锁、分布式事务 |
| RabbitMQ 用于跨网关送帧、用户服务异步请求与响应 | 暂不建设持久化审计服务 |
| Redis 存路由、服务地址、共享状态与验证码 | 不把 Redis 当成可以保存 socket 的地方 |
| 新建 User Service，用户数据存 PostgreSQL | 不让用户登录 token 替代设备所有者授权 |

**第一版部署多个 Gateway、一个 Core Service、一个 User Service。** Core 先保持单实例，集中管理状态变更，避免一开始就处理多份业务状态之间的协调问题。它仍然是单点，这一版不承诺全系统高可用。

## 2. 整体架构

```text
Agent / yiuk-mcp                         Qt 设备客户端
       │                                      │
       └────────────── WSS ───────────────────┘
                         │
                    Nginx stream
                  （L4 转发长连接）
                         │
                 ┌───────┴───────┐
                 ▼               ▼
             Gateway-1       Gateway-2
             本地连接表       本地连接表
                 │               │
                 ├──── gRPC ─────┤────► Core Service（先单实例）
                 │               │     设备 / 会话 / 命令 / 文件传输
                 │               │
                 └── RabbitMQ ───┘
                     ├─ 跨网关送帧
                     └─ 用户请求 / 结果 ◄──► User Service
                                               │
                                           PostgreSQL
                                           用户数据

Redis：网关与服务地址、连接归属、Core 共享状态、验证码（按阶段接入）
Docker Compose：统一启动上述组件
```

### 每个组件只记一句话

| 组件 | 职责 |
| --- | --- |
| **Nginx** | 将新连接分配给不同 Gateway，已建立的长连接仍由原 Gateway 承接 |
| **Gateway** | 管 socket、心跳、协议解析、请求分流和帧投递，不做核心业务裁决 |
| **Core Service** | 原平台的业务整体：注册设备、校验密码、申请与关闭会话、管理任务和传输 |
| **User Service** | 新用户领域：注册、登录、邮箱验证、头像管理、JWT 签发等 |
| **Redis** | 告诉大家“服务在哪里、连接在哪里”，并按需要共享状态与存临时数据 |
| **RabbitMQ** | 把帧送到对应 Gateway；在 Gateway 与 User Service 之间传请求与结果 |
| **PostgreSQL** | 持久化用户数据，暂不承担平台任务与输出归档 |

Gateway 与 Core 之间使用 gRPC，因为注册设备、校验会话等操作需要拿到业务处理结果。用户系统采用 MQ 请求/响应，是本计划的选择，**不是因为登录天然不需要等待结果**。

## 3. 断线策略：重新连接，不恢复旧会话

沿用现有方向，不再将“会话可恢复”列为 P0：

1. 连接断开后，旧会话按原规则中断，未完成任务按现有失败收敛规则处理。
2. Agent 需要继续协助时，重新连接平台，再调用 `request_connection` **创建新会话**。
3. 已持有当前设备临时密码时，密码有效、未撤销且设备在线，就可以直接创建新会话，无需再次审批。
4. 没有有效密码时，仍需设备所有者审批。
5. **新建会话不等于重放旧命令**。旧任务可能已部分执行，Agent 应先检查实际情况，不能看到断线就重新执行安装、删除等操作。

这样不需要换绑旧会话，也不需要续接旧输出。代价是网络中断、网关重启时，正在进行的协助可能结束；本计划接受这一边界。

### “批准后把密码返回 Agent”是另一项产品改动

这是计划中的便利功能，**不是当前代码已实现的行为**：目前审批成功的响应不会把设备临时密码返回给 Agent，服务端只保存密码的盐与哈希，不能从哈希还原明文。

若实施，应由设备端在所有者知情的情况下通过受保护的链路提供凭据，而不是尝试从服务端哈希中恢复。需要明确告知所有者：**这次批准还将允许对方在密码有效期内再次直连**；关闭本次会话不等于撤销该密码。密码不得进入日志或公开事件队列。

这项功能可独立开发，不作为多网关的前置条件。

## 4. 原有业务怎么迁：整体搬到 Core，不逐个拆

### Gateway 留下什么

- WSS 连接接入与关闭、连接 ID、本机 `connection_id → socket` 表；
- 心跳、基础帧大小检查、JSON 编解码；
- 调用 Core，将 Core 返回或推送的消息送到对应连接；
- 接收 RabbitMQ 中发给本节点的帧，写入本地有界发送队列；
- 连接断开时通知 Core；节点异常退出时依靠节点存活信息收敛受影响连接。

### Core 搬走什么

- `device.Manager`：设备码、密码校验、墓碑、设备业务状态；
- `session.Manager`：会话申请、批准、有效期、归属与关闭；
- `task.Manager`：命令状态、幂等键、输出缓存与查询；
- `transfer.Manager`：传输记账、序号与大小检查；
- 相关业务 handler 与过期清理逻辑。

原来 handler 里直接查 `Server.connections`、直接写 socket 的地方，需要换成“查目标连接归属并投递”的接口。**整体迁移不等于不改代码，只是不改变这几个业务模块之间的边界。**

先由单个 Core 处理业务变更与定时清理，复用现有进程内同步方式。以后真的需要多个 Core，再单独设计并发状态更新，而不是这次顺手引入全套分布式协调。

### 4.1 P1 的实际边界（已实现）

P1 没有按“逐个接口定义业务 RPC”的做法，而是**整帧透传**：Gateway 从客户端读到什么字节就送什么字节，Core 编解码，只传原始帧。

```text
internal/platform/core      业务：认证/设备/会话/命令/传输/过期清理（不认识 socket）
internal/platform/gateway   接入：监听/连接表/队列/心跳/超时（不认识业务）
internal/platform/edge      gRPC 契约与两端适配（edgepb/ 为生成代码）
```

契约只有两个服务、四个方法：

| 服务 | 提供方 | 方法 | 作用 |
| --- | --- | --- | --- |
| `Edge` | core | `Handle` | gateway 把一帧交上来，返回更新后的身份；致命错误附带回写帧 |
| `Edge` | core | `Detach` | 连接关闭后收敛该连接名下的会话 |
| `Push` | gateway | `Deliver` | core 把出站帧写进某条连接的发送队列 |
| `Push` | gateway | `Alive` | core 问“这条连接还挂着吗” |

Frame 就是客户端原始 JSON 字节，两个进程都不需要为每种消息写一遍 schema。

三个必须遵守的约束：

1. **单连接保序**：Gateway 对同一条连接一次只发一个 `Handle`，收到回复再读下一帧。不要在 Core 里再加并发处理，否则 `open_session_channel` 与 `execute_command` 会超车。
2. **Core 只有一个出口**：出站帧全部走 `Link.Deliver`，没有第二条写 socket 的路径；异步推送（过期清理）与直接响应走同一个出口。
3. **不要 Core 自己记账**：连接表只在 Gateway，Core 判断连接死活时调 `Alive`。“投递失败”就等于“设备不可用”，不要先把帧记成已发送。

`cmd/platform` 保留单进程模式：同一套 core + gateway，进程内直连，不走 gRPC。

## 5. Redis：先登记位置，再按需要外置状态

先做两类简单记录：

```text
服务地址：service:core:core-1      → 内网 gRPC 地址、实例标识（带 TTL）
网关存活：gateway:gw-1            → 本次启动标识、内网信息（带 TTL）
连接归属：route:conn:<conn_id>    → gateway_id + 本次启动标识（带 TTL）
设备路由：route:device:<device_id> → conn_id + gateway_id（带 TTL）
```

- 服务启动时注册地址，定时续期；正常退出主动移除，异常退出等 TTL 失效。
- Gateway 连接认证、设备注册完成后更新路由；断线时清理自己拥有的那份记录。
- 清理旧记录前必须确认仍属于原连接，避免旧连接的迟到清理删掉新路由。
- **路由只解决寻址，不授予设备操作权**；会话是否有效仍由 Core 判断。

Core 的设备、会话与任务元数据可以逐步接入 Redis；第一版不要求把所有 map 一次搬完。验证码、频率计数等短期数据也适合放 Redis。命令输出先留在 Core 的有界内存缓存，并给终态记录设置回收策略，不在这一版引入对象存储。

**数据放进 Redis 不等于获得持久化或自动恢复能力。** TTL、Redis 重启策略、Core 重启时哪些记录失效需要明确；第一版仍不恢复旧会话。单 Core 也不意味着多条 Redis 命令天然原子，未来外置需要“先判断再写入”的逻辑时，再针对具体操作选择原子命令、事务或短脚本。

## 6. RabbitMQ 用途一：跨网关送帧

### 场景

操作者连 Gateway-1，设备连 Gateway-2。Gateway-1 查不到设备 socket，因为它在另一台进程里。

```text
操作者
  → Gateway-1
  → gRPC 调 Core：校验会话、登记任务、确定目标连接
  → Gateway-1 按投递指令查 Redis 路由
  → RabbitMQ（目标 Gateway-2 的队列）
  → Gateway-2 的本地发送队列
  → 设备

设备输出
  → Gateway-2
  → Core：记录输出与任务状态
  → 按相同方式投递到 Gateway-1
  → 操作者
```

这是正常请求的示例。Core 主动产生的过期、取消等通知也走统一投递出口；落地时可由 Core 使用同一 MQ 发布器发往目标网关。**所有发往某连接的业务帧应经过统一的有序出口**，不要一部分直写、一部分绕 MQ，导致相互超车。

### 简单队列规划

```text
exchange：agentremote.gateway（direct）
routing key：目标网关的本次启动标识
queue：gateway.<本次启动标识>（每个网关一个）
```

帧外层带目标 `connection_id`、网关本次启动标识和原业务消息。接收方确认目标连接仍属于本节点、本次启动，再投递。旧节点的消息不能因为节点名复用而送进新连接。

### 先把边界定清楚

- 单队列、单消费者串行处理，减少消费侧乱序；**它本身不能保证多个生产者之间的业务顺序**，发送端也要按连接/任务顺序发布。
- 跨网关帧不作为离线任务积压，不做断线后自动重放。可使用临时队列、消息短 TTL、队列长度/字节上限。
- 自动确认可作为第一版允许丢帧的选择，但表示消息可能在本地投递前丢失；**不持久化本身不能防止重投，单靠几个 MQ 开关也不能保证端到端“恰好一次”**。
- 检查发布错误与无路由返回；MQ 不可用、目标节点失效时及时失败收敛，不能一直报告成功。
- 不确定命令是否执行时，报告 `result_unknown`，不自动重发命令。必要的取消控制也不能承诺一定送达。

### 文件分块怎么办

设备与操作者分属两个 Gateway 时，文件块同样需要跨节点送达，不能一边声明“所有跨网关帧走 MQ”，一边完全排除文件块。

第一版可沿用现有小块协议，经同一投递层转发，保留序号、大小和 SHA-256 校验；**不把整个文件塞进一条 MQ 消息**。同时约束在途块数、队列字节数和超时，测试慢设备下的背压。若以后文件流量影响控制消息，再考虑独立队列或直连流通道，本次不增加第二套传输架构。

## 7. RabbitMQ 用途二：User Service 异步请求与响应

### 职责

User Service 负责注册、登录、邮箱验证、头像资料、密码哈希、JWT 等用户业务，用户数据写 PostgreSQL。它不管理设备会话，也不调度 PowerShell。

```text
客户端 → Gateway → RabbitMQ 用户请求队列 → User Service
                                                   │
                                                   ▼
                                               PostgreSQL
                                                   │
客户端 ← Gateway ← 本网关专属结果队列 ←──────────────┘
```

### 怎么知道结果属于哪个请求

沿用已经熟悉的“关联编号”思路，但这是**新增的内部 MQ 往返**，与现有 operator ↔ 平台的 `correlation_id` 不要混淆：

1. Gateway 生成内部关联编号，登记 `编号 → 等待者/客户端连接`。
2. 发布请求，携带操作名、参数、关联编号、`reply_to`（本网关结果队列）与截止时间。
3. User Service 处理后，将相同关联编号放入结果，发到 `reply_to`。
4. Gateway 找到等待者，把结果返回客户端；超时则清理等待记录，迟到结果不误投给下一次请求。

登录/注册仍需要最终结果，只是传递方式经过 MQ。第一版可以让 Gateway 在有限时间内等待；邮件发送这类耗时操作可先返回“已受理”，再查询状态。**MQ 超时不等于业务一定没完成**，注册等写操作应有独立业务请求号做去重，重复请求不能重复建用户或无限发邮件。

### 数据与安全

- PostgreSQL 存用户与资料；Redis 可存验证码、有效期与限流计数。
- 密码只存适当的密码哈希，不存明文；密码、验证码、JWT 不写业务日志。
- 用户请求队列不是广播通道：限制访问权限、有效期与积压，敏感字段只传给指定服务。
- 请求消费可在处理成功后手动确认；重复投递靠业务去重处理。若需要可靠发布，再配合发布确认与明确的持久化配置，不能把“有 ack”当作绝不丢的保证。
- JWT 证明用户身份，不替代设备临时密码或所有者审批。网关只有拿到明确的认证成功结果，才能建立已认证身份；服务不可用时不能默认放行。
- 旧 `player_password` 路径先保留，避免服务器上的 pi 部署被强制中断；以后是否淘汰另行决定。

## 8. 审计：暂不作为改造前置条件

当前保留 `slog`，不单独拆 audit-svc，不强制引入审计数据库或 MQ 消费者。**日志是否重启后还在，取决于文件/容器日志配置，不等同于业务状态在内存中就一定丢日志。**

以后确实需要历史查询与追责，再增加：

```text
Core / Gateway → RabbitMQ 审计队列 → 审计消费者 → 数据库
```

审计事件与实时帧分开配置可靠性、限流与保留时间；使用事件 ID 去重，不记录临时密码、命令正文与完整输出。

## 9. 按什么顺序做

| 阶段 | 做什么 | 验收 |
| --- | --- | --- |
| **P1：接入/业务分离** ✅ | 一个 Gateway + 一个 Core，用 gRPC 连接；原业务整体迁移 | 注册、审批、命令、上传下载、关闭会话全部回归通过；单 Core 统一清理过期状态 |
| **P2：Redis 登记位置** | 服务地址、节点存活、连接归属；业务状态按需要逐步外置 | 查得到服务和连接；旧连接清理不误删新路由；节点退出后路由能失效 |
| **P3：多网关** | 第二个 Gateway、Nginx、RabbitMQ 跨网关投递 | 两端刻意连接不同 Gateway，命令与文件双向跑通；断线、MQ 故障、慢设备能收敛 |
| **P4：用户微服务** | User Service + PostgreSQL，通过 MQ 请求/响应 | 注册登录、邮箱验证、结果关联、超时及重复请求可测；旧 Agent 认证路径仍可用 |
| **后续：按需补齐** | 审计落库、更多监控、性能优化 | 有真实需求再做，不计入当前必做项 |

用 Docker Compose 统一编排，先在单机多进程验证，再搬到多台机器。Nginx 先选 L4 透传以保留现有 TLS 校验方式；各 Gateway 需提供客户端信任的证书。**L7 TLS 终止并非绝对不能做，只是需要同步设计证书信任与固定指纹迁移，本次不做。**

## 10. 第一版必须讲清楚的限制

- Gateway 可多开，不代表 Core、Redis、RabbitMQ、PostgreSQL 都已经高可用。
- 不恢复旧会话；只保证后续可以重新建立连接、重新请求协助，不保证旧任务继续。
- 原来的 `request_id` 幂等、`correlation_id` 配对应答、输出预算、传输校验继续保留。
- session 创建并不等于批准。只有有效且已批准的会话才可操作，默认具备命令执行与文件读写能力。
- 网关重启会中断本节点连接；Core 重启按统一策略中断旧会话，不能让 Redis 中的残留记录被误认为仍然授权有效。
- 不承诺“消息绝不丢”“全链路绝不重复”；超时和失联时如实报告，破坏性操作不盲重试。
